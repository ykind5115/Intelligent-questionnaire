## 1. 调研问题

「节点图编辑器」（node-based graph editor，又叫有向图可视化编辑器）——
即用**画布 + 节点 + 连线**来编辑流程的界面范式，业界代表是
Unreal Blueprints、Blender 节点、n8n / Zapier 工作流、ComfyUI。

本项目的问卷结构天然是一张有向无环图（DAG）：题目是节点、跳转是边。
来源文档 `文档一.md:15` 明确要求「问卷DAG编辑器（题目节点、分支跳转连线、条件配置）」。

**要回答的问题**：这件事该不该做、该什么时候做、用现成库还是自研。

## 2. 本项目的硬约束（决定选型，先摆出来）

| # | 约束 | 出处 | 对选型的影响 |
| --- | --- | --- | --- |
| 1 | 前端**无构建链**，原生 ES 模块，`<script type="module">` 直载 | AGENT.md 第 7 节 | 排除所有**要求打包**的库（React Flow / Rete / LiteGraph 的 npm 形态） |
| 2 | **运行时不访问公网**（后期整体迁到内网） | 决策 D13 | 排除**运行时 CDN**；但库可以 `npm` 装上、随项目一起复制到内网 |
| 3 | 现在没有任何前端框架（node_modules 里无 react / vue） | 本次核实 | 只说明「现在没装」，**不构成约束** —— 见下方订正 |

> ## ⚠️ 订正（2026-10-15，由需求方指出）
>
> 本节初稿有**两条推理错误**，已改正：
>
> 1. **把「现在没装 react」当成了「不能用 react」。** 这两件事完全不同：
>    React 完全可以现在 `pnpm add`，随项目一起复制到内网。**这不是约束。**
> 2. **把「前端资源零外部 URL」当成了「不能引入库」。** 同理 ——
>    库文件可以自托管进 `public/`。真正的约束只有「**运行时**不能拉 CDN」。
>
> 因此**成立**的硬约束只有两条：
> - **没有构建链** → 不能选「必须经过打包器」的库；
> - **运行时无公网** → 不能运行时从 CDN 加载（要么自托管，要么先装进仓库）。
>
> 这会放宽选型空间：凡是提供**浏览器可直接引入的单文件产物**（UMD/IIFE），
> 或者不依赖打包的库，都可以用。React Flow 这类需要 JSX 编译的仍然排除，
> 但那是因为**构建链**，不是因为「不能用 React」。
>
> 下文的对比表已按此口径标注，但个别「主要代价」一栏仍带着初稿的偏严语气，
> 阅读时以本条订正为准。

## 3. 候选方案对比

| 方案 | 渲染 | 许可 | 无构建链可用性 | 主要代价 |
| --- | --- | --- | --- | --- |
| **自研（SVG + 原生 DOM/指针事件）** | 自定 | — | ✅ 原生 | 命中检测、吸附、缩放、触摸都要自己写 |
| **[AntV X6](https://x6.antv.antgroup.com/)** | SVG / HTML | **MIT** | ⚠️ **有单文件 UMD**（见下），但只挂全局 `window.X6` | 体积 + **样式要重做**；官方文档对初学者不友好 |
| [React Flow / xyflow](https://reactflow.dev/) | DOM | MIT | ❌ 需要 React + 打包 | 与约束 1、2 直接冲突 |
| [Rete.js](https://retejs.org/) | DOM | MIT | ❌ npm/打包导向 | 同上 |
| ngraph / LiteGraph | Canvas | MIT | ❌ 需打包 | 同上 |
| [LogicFlow](https://github.com/didi/LogicFlow)（滴滴） | SVG | MIT | ❌ npm 导向 | 同类问题；另有「更新节奏」疑虑 |
| [butterfly-dag](https://github.com/alibaba/butterfly)（阿里） | DOM | MIT | ❌ npm 导向 | 偏 React 生态 |
| [jsPlumb](https://github.com/jsplumb/community-edition) | DOM | 社区版（注意许可分层） | ⚠️ 历史上有全局脚本形态 | 自定义节点成本高；许可需逐版本确认 |
| [Drawflow](https://github.com/jerosoler/Drawflow) | DOM | MIT | ⚠️ 零依赖、偏独立使用 | 节点内表单能力弱，风格与现有页面差异大 |
| [Cytoscape.js](https://js.cytoscape.org/) | Canvas | MIT | ✅ 有独立分发 | **偏图分析**而非图编辑，自定表单节点成本高 |
| [dagre](https://github.com/dagrejs/dagre) / [elkjs](https://github.com/kieler/elkjs) | — | MIT / EPL | ✅ 纯计算 | 只是**布局算法**，不是编辑器；可与自研组合 |

**X6 的可用性已核实到文件级**：`@antv/x6` 3.1.8，MIT，
npm 包内含 `dist/x6.min.js`（约 570 KB），是浏览器可直接引入的单文件产物。

## 4. 关键判断：这件事的收益取决于「分支」是否已存在

这是本次调研最重要的结论，也是**推翻了直觉**的一点：

> **画布的价值来自「连线」。没有分支逻辑，画布上就没有连线可画 ——
> 那么画布相对列表的唯一增量仅剩「空间布局」。**

- 我们当前的编辑器是**列表式拖拽**（§4.11），已经能表达顺序、分组、增删改。
- 在没有条件分支的问卷里，「顺序」用列表表达**比画布更直观**：
  阅读方向单一、移动端可用、无需平移缩放。
- 因此：**画布应当建立在 L1（条件分支）之上，而不是先于它**。
  这与 §4.11 当初「列表式拖拽」的决定一致，本次调研进一步确认它不是妥协，
  而是正确顺序。

**结论：先有分支，再有画布。**

## 5. 三条路线与建议

### 路线 A：只读 DAG 预览（推荐先做）

纯 SVG 自研，**不引入任何库**，复用后端已有的结构：

- 输入：`current_schema.sections[].questions[]`；
- 输出：分层布局（自上而下或从左到右）+ 连线（顺序边；将来分支边用不同颜色/线型区分）；
- 交互：仅缩放/平移；点击节点**联动左侧表单**（同一份数据两种视图）。

**成本**：小。**风险**：低（不改数据模型、不新增依赖）。
**收益**：中高 —— 直接解决 Lensym 那篇反复强调的问题：
「15 条以上跳转规则时，列表里没人能看出完整流程」。

### 路线 B：可交互连线编辑（需要 L1 先落地）

在路线 A 的基础上加「拉线建分支」。这里才真正需要决策「自研 vs X6」：

| | 自研 | 自托管 X6 |
| --- | --- | --- |
| 依赖 | 0 | 570 KB 单文件 + 自写 shim |
| 与现有 ESM 一致性 | 完全一致 | 需要一段「加载全局 → 导出模块」的适配代码 |
| 命中/吸附/缩放/触摸 | 自己写 | 现成 |
| 视觉风格 | 天然一致 | 需要覆盖样式 |
| 内网部署 | 无影响 | 需把文件纳入 `public/`（可行） |

**倾向**：若分支规则的结构简单（§4 的 `branches` / `defaultNext` 是**指针**，
不是任意连线的 DAG），自研的成本被高估了 —— 因为**要连的线是有限且固定的**：
每题最多几条分支 + 默认出口。真正的「自由连线」在这个数据模型里并不存在。

### 路线 C：把结构改成真正的图存储

即行式 `template_node/edge` + `instance_node/edge`。**已由 D16 否决**，
本调研不改变该结论 —— 画布是**视图**，不需要为视图换存储。

## 6. 设计时校验清单（可直接对照实现）

业界对「图式问卷逻辑」的论述与我们在 §4.7 制定的校验规则高度一致。
[Lensym 的图式问卷逻辑文章](https://lensym.com/blog/graph-based-survey-logic)
给出了一份可复用的检查表，逐条对照本项目：

| 检查项 | 危害 | 本项目的落点 |
| --- | --- | --- |
| 孤立节点（从入口不可达） | 有题目永远没人看到 | §4.7 的 **V5**（告警不阻断） |
| 死路（到不了终点） | 答题者卡在中间 | §4.7 的 **V2**（拒绝写入） |
| 条件矛盾（不可能成立） | 分支永远走不到 | 当前未覆盖，属后续增强 |
| 无限循环（无终止条件） | 答题者被困 | §4.6 的环判定（`maxSteps` 收敛检测） |
| 条件缺失（无合法下一步） | 没有可走的出口 | §4.4 的顺序语义第 2 条（兜底走下一题，故天然不会缺） |
| 终点不可达 | 问卷无法完成 | §4.7 的 **V4** |

**差异点**：本项目把「缺省推进」定义为「按 `order` 走下一题」，
因此「条件缺失」这一类问题在结构上被消除了 —— 这是比 Lensym 描述的做法更省心的一点。

该文的另一个观点值得记下：**列表式 skip logic 在复杂设计下会产生「看不见的错误」**
（孤立题、死路、条件矛盾只在收数据时才暴露）。这正好是路线 A 只读预览的立项理由 ——
预览的价值不只是好看，而是**让结构性错误在编辑期就可见**。

## 7. 调研结论

1. **现在不做连线画布。** 画布价值来自连线，连线来自分支，而分支（L1）尚未排期。
2. **但「只读 DAG 预览」（路线 A）值得单独做**，且不依赖 L1 ——
   可以先画顺序边，等分支落地后自然升级为带条件的分支边。
3. **CDN 方案被两条硬约束否决**（前端零外部资源 + 内网迁移）。
   若将来要用库，必须自托管进 `public/`，并接受一段 ESM 适配代码。
4. **不建议换存储**（与 D16 一致）。画布是视图，不是第二份真相。
5. **真实缺口不是「缺画布」，而是「缺分支」**。先补 L1，收益远大于先做画布。

---

## 8. 若要做，建议的验收标准

- 预览必须能标出：不可达题目、无终点的路径、多路径汇聚点；
- 点击节点能定位到左侧对应题目（视图与表单双向联动，单一真相源）；
- 纯只读预览**不新增任何运行时依赖**；
- 节点数 100+ 时仍可交互（本项目实测单份问卷平均 17 题、最大也不大，
  因此性能不是主要风险）。
