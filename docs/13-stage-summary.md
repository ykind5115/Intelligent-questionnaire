## 2. 本阶段做了什么

本阶段共 16 个提交，可归为四批：

### 2.1 文档基线（把游离的三份文档收编）

`docs/` 下曾出现三份来源文档（`文档一.md`、`问卷系统数据库设计文档.md`、
`问卷系统数据库模型图.html`），提出用「模板/实例双套 DAG 邻接表」取代现有 JSONB 方案。

**核实结论：11 张表里 7 张的能力现有设计已具备**，真正缺的只有条件分支等少数几项。
据此形成 **决策 D16**：不换表、分支用显式字段、行式 DAG 表推迟。
调研与分阶段计划记入 [11](11-future-capability-plan.md)，
画布选型记入 [12](12-node-graph-editor-research.md)。

### 2.2 L2：独立小改进

| 能力 | 落点 |
| --- | --- |
| 模板分类 | 新表 `questionnaire_template_categories` + `templates.category_id` + 筛选 + 管理界面 |
| 实例可读编号 | `instance_no`（`INS-YYYYMMDD-NNNN`）+ 发号表 + 存量回填脚本 |
| 案件信息结构化 | `subject_info` 从 `z.record` 改为显式 Schema（保留未知字段） |
| 建案标题 | 不再预填「模板名 + 日期」这种看起来填好了的默认值 |

### 2.3 编辑器：列表视图 + 节点画布

**列表视图**（`editor.html` + `editor.js`）：手工从零建、加载模板改、加载模板看，
原生 HTML5 拖拽排序（零依赖）。为它补齐了后端缺失的三个操作
（`remove_section` / `reorder_sections` / `reorder_questions`）。

**节点画布**（`editor-graph.js`，自研 SVG，零依赖）：与列表视图并存、可切换。
题目作为节点、三类边表达跳转关系（顺序 / 分支 / 终点），
支持拖拽定位、缩放平移、**拉线建分支**、自动布局。
坐标存在结构根的 `layout` 里，写入**只更新该键**（`jsonb_set`），
因此拖节点不会碰结构、不产生审计，也不会与结构编辑互相覆盖。

### 2.4 L1：条件分支（本阶段最大的一块）

| 层 | 内容 |
| --- | --- |
| 结构 | 题目加 `branches`（按序取第一条命中）与 `defaultNext`（省略=按顺序 / `null`=终点 / 字符串=跳转） |
| 求值 | `resolveFlow` 纯函数；**环检测用「步数超上限」而非「重复节点」**（汇聚是合法 DAG） |
| 校验 | 悬空引用、比较值类型与选项归属、无出口环 → 400；**不可达题目只告警** |
| AI | 第 8 个工具 `set_question_branch`（整体替换语义） |
| REST | `PATCH .../questions/:id/branch`；只读预览 `GET .../flow/structure`、`POST .../flow/cases` |
| 编辑器 | 行内分支摘要 + 配置弹窗（控件随题型变化）+ 不可达告警定位 + 弹窗内只读预览 |
| 答卷 | **答案按路径定序**、响应带 `flow.questionIds`、**必填只校验路径内的题目** |

## 3. 关键设计决策（现在为什么是这样）

摘录影响面最大、且容易被后来者误解的几条。完整清单见 [09](09-review-and-decisions.md)。

| 决策 | 内容 | 为什么 |
| --- | --- | --- |
| **D1** | 下发即冻结结构；要改先撤回 | 调查内容一旦布置就是业务边界，改结构必须显式 |
| **D2** | 个案改动可「扶正」为模板新版本（**生成草稿，不自动发布**） | 模板是全组织共享资产，不能因个案需求被静默覆盖 |
| **D9** | 一次 Tool 调用 = 一个 `operation_id` = 一次 Revision | 幂等与审计的粒度都靠它 |
| **D16** | **不换表**；分支用 JSONB 里的显式字段；行式 DAG 表推迟 | 结构是「整份读写」的语义，换成行式表要重写纯函数 Operation 层；而分支用指针即可表达 |

**三条容易被误解的取舍**（都在代码注释里写明了原因）：

1. **分支的环检测不看「有没有环」，看「能否收敛」。**
   多路径汇聚到同一题是合法 DAG，「重复即环」会误杀；
   无出口的环会让路径无限增长，用步数上限拦下即可。
2. **必填只校验「本次路径内」的题目。**
   分支跳过一道必填题时它不该阻塞提交 —— 否则「是否飞过？→ 否」会让后面的
   「飞行地点」变成永远填不上的死结。
3. **允许分支条件引用题目自己。**
   这正是「按本题答案决定是否跳过本题」的常用写法
   （「是否飞过？→ 否 → 跳过飞行细节」）。求值顺序是「本题记为走过 → 立即跳走」。

## 5. 已验证 / 未验证（重要）

诚实区分这两类是本文档的主要用途之一 —— 本项目历史上出现过
「进度表声称链路已通、实际整条链路不可用」的情况。

### 已验证

- `pnpm typecheck` 通过；`pnpm lint` 0 问题；`pnpm test` **25 文件 / 455 用例全绿**；
- 数据库基线可复现：跑完全量测试后各表回到运行前状态（测试自带清理）；
- 迁移在真实库上执行过，存量数据完好（执行前后逐表核对）；
- 存量实例编号已回填，`instance_no` 无空值、格式统一、无重复；
- 分支的语义正确性有纯函数单元测试覆盖（含汇聚、环、自引用门控、悬空引用）；
- 答卷链路的分支行为有真实 HTTP + 真实库的集成测试覆盖
  （答是/答否得到不同题序、被跳过的必填不阻塞提交、路径内必填仍拦截）。

### 未验证

- **前端交互没有做过浏览器实测。** AGENT.md 第 0/9 节禁止代理启动常驻服务，
  因此拖拽手感、弹窗联动、预览渲染、模板分类弹窗等**只做了静态审查与语法检查**。
  这些需要人工点一遍。
- **AI 链路的真实模型评测没有量化数字。** D5 的评测用例集已建好，
  但只用假 Provider 跑过（验证评测器与链路），**没有用真实模型跑出成功率**。
- **节点画布的交互没有做过浏览器实测**（同上：代理不能起服务）。
  拖拽手感、拉线建分支、缩放平移、自动布局都只做了静态审查。
- 撤销/重做、触屏手势未实现 / 未验证。
- 性能未压测：单份问卷节点量级小（实测平均 17 题），池上限默认 5（`DB_POOL_MAX`）。

## 6. 已知缺口与风险

### 6.1 功能缺口（按建议优先级）

1. **答卷填写页与审核页缺失** —— 目前只能走 API。
   这是**最实际的缺口**：分支能力最终要靠填写页才真正被人用到。
2. **`applyToTemplateVersion` 的乐观锁形同虚设** —— 它用 `versionNo` 当乐观锁，
   而 `versionNo` 在同一版本生命周期内**不变**，因此两人同时编辑同一草稿时锁不住，
   后写者会覆盖先写者。这是**既有设计问题**，本次未改动。
3. 模板发布流程较简陋（无审批、无发布前预览检查）。
4. 分类没有独立权限细分，也没有拖拽排序。

### 6.2 工程化缺口

- `lint` / `format` 脚本不可用（依赖缺失）；
- 无 CI（本地跑测试）；
- 未做演练/预发环境（决策 D13 是后期整体迁内网）。

### 6.3 需要在真实使用中回答的问题

- **是否真的需要连线画布？** 见 [12](12-node-graph-editor-research.md) 与 11 第 4.11 节：
  画布的真实增量是「同时看见全部分支的相对位置」，**分支数量很多时才明显**；
  当前的表单配置 + 行内摘要 + 路径预览已覆盖主要价值。建议先用一段时间再定。
- 单份问卷的实际分支数量分布（决定上面那个问题的答案）。

1. 分支的语义细节（尤其是「汇聚合法」「必填只看路径内」「条件可引用自己」）
   都有注释与测试，**改之前先读 `operations/flow.ts` 的注释**；

3. 改动完成后必须让数据库回到基线，测试自带清理，不要手写一刀切的清理语句。
